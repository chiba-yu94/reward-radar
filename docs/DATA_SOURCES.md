# Sources

`data/sources.json` records provider, official evidence, exact approved destination, country scope, language, permission basis, method, cadence and review date. Last successful run and errors are recorded by Actions artifacts and in the local SQLite source observation. Registry values for last automatic run are initially null.

## Add or revise a source

1. Read the provider's official eligibility, dates, spending, method, and payout rules. Check the participation page and any redirect destinations. Record the official links and the actual review date.
2. Choose `manual` and `editorial-summary` for independently written facts with links. Keep the provider's copy, HTML, images, branding assets and program directory out of publication. A manual source is never fetched by the scheduled collector.
3. Before adding automation, document the official API or feed, applicable terms, access and reuse scope, robots directives when applicable, rate limit and exact endpoint. A permissive robots file does not authorize redistribution. The current adapter is deliberately limited to reviewed files in GitHub's official docs repository. Add an adapter with equivalent URL controls and fixtures to support a different provider.
4. Add the bilingual record. Use a country list only where explicit, null for unverified, and `worldwide_reviewed: true` in the source registry only where the official source explicitly permits worldwide participation. When a country list is partial, explain that in both translations. Keep amounts, currency, cost or times null if missing. For purchase-only programs with a variable price, use `kind: purchase` and null amount.
5. Review the changes and run `npm test`. Changed sources and destinations stay pending until the reviewed inputs are updated. For GitHub Contents, a new blob identifier requires review of the underlying file and any referenced conditions.

## Discovery and review

`data/discovery-sources.json` contains reviewed Japanese, UK, US and international sources. The daily `Discover giveaway and skill-competition candidates` workflow reads official RSS/Atom, selected publisher announcements and indexes, and documented competition APIs. Feed and index observations are compared with the prior run. A bounded subset of newly seen or updated links is inspected on the reviewed host; announced rules PDFs are read where a source has explicit extraction rules. This evidence supports editorial review. A source market is the location of the source, and entrant eligibility still comes from the official rules.

The queue (`var/candidates.json`) and snapshot (`var/discovery-state.json`) are saved as separate 30-day Actions artifacts. Known official publication, opening and deadline fields come from source evidence. The first-observed date comes from the saved snapshot. Local execution with separate paths is supported using `python3 -m radar.discovery --state var/discovery-state.json --output var/candidates.json`. Install `requirements-discovery.txt` into a virtual environment for PDF parsing. Source errors and page bounds are reported independently. A restored snapshot is required to preserve first-observed dates across runners or machines.

Make.fun uses the documented public competition API and Kaggle uses its authenticated read-only competition list. The Kaggle job takes `KAGGLE_DISCOVERY_TOKEN` as a repository secret. Local runs can use `KAGGLE_API_TOKEN` or the standard `~/.kaggle/access_token`. The SIGNATE company news sitemap and organizer announcements supply SIGNATE links. The Kiro event index and Cognizant announcements supply Devpost links. The collector does not request Devpost pages, whose hackathon terms restrict automated retrieval. The Hackathon Raptors project index supplies independently hosted events such as Agentware. Skill opportunities require review of fees, payout conditions, geography, AI use and the actual registration cutoff. A reported prize pool is distinct from the amount an individual winner may receive.

For new websites, add a reviewed entry with `kind`, `endpoint`, `permission_url`, source market, lane and time zone. For an `index` or `sitemap`, set a narrow `article_path` and `detail_limit`. Add a `page` entry for an exact publisher announcement or rotating rules page. Configure `date_patterns` only for explicit dates and use `rules_pdf` / `pdf_date_patterns` for known official PDFs. Keep the publisher evidence URL when a registration link is on another domain. Browser scripts, registration forms, competition submissions and wallet endpoints are outside this collection path.

OpenAI Responses `web_search` looks for original campaigns and rules pages in Japan, the UK and the US. A run sends one request per market with `gpt-5.6-luna` and a limit of one web tool call per request. The collector saves only cited HTTPS URLs, search market and usage counts under `source_leads`. Treat each URL as a lead for editorial review. The collector makes no direct requests to discovered URLs. The daily workflow uses `OPENAI_API_KEY` from the main-only `freebie-trail-api` environment when `FREEBIE_SOURCE_SEARCH_ENABLED=true`. Manual runs require `include_source_search`, and workflow reruns skip the API call. Local use requires the same flag and a project API key. The scheduled search limit in a 31-day month is 93 web tool calls, before any manual runs. [OpenAI web search](https://developers.openai.com/api/docs/guides/tools-web-search) · [API pricing](https://developers.openai.com/api/docs/pricing#tools)

For each candidate, verify the organizer, original rules, all redirects, geographic and age restrictions, entry cost and prize claim, personal information at both stages, translations and expiry. Only then add the exact source and destination to an approved registry. Dated campaign deadlines are converted from the provider's time zone. If a Japanese source only states a date, display the date without a time and stop listing it after that date in Japan.

Free sweepstakes need documented organizer, cost and privacy checks. Cash, gift-card, electronics and other exceptional prizes additionally require explicit country eligibility and known data requirements for entry and claim. Check fees, impersonation indicators, official claim channel and prize details before setting the enhanced review flag. A shipping-only restriction never supplies missing evidence about residence.

## Quest board and application guides

Use `data/editorial.json` for quest reviews and site-hosted articles. The existing discovery job writes URLs for review to `var/candidates.json`. Editors can use those URLs or other official public pages to start a quest review. The publisher emits quests from the reviewed registry and has no path from the RSS output to public listings. The Yamanashi candidate uses manual review of the official site and rules.

- Record an unresolved quest with `status: candidate`, its official source and the gaps in the review. Before switching to `approved`, check that the official rules establish current acceptance, eligibility from Japan, no up-front payment or deposit, and how the reward is paid. When the site owner explicitly approves a listing whose official rules omit residency, record `review.japan_eligible: "not-stated"`. The board and detail page label residency eligibility as unconfirmed. Report any prize redemption territory separately. Record the review date, the official listing and evidence URLs, the closing timestamp, and the task, eligibility, reward conditions and payment method in each available language. Use `completion` for completion fees, `selection` for accepted work and `prize` for competition winners. For a date-only cutoff, follow the opportunity convention of recording the last second of the final local date and setting `deadline_date_only` to true.
- Change a quest to `closed` when the organizer closes it early. The build excludes candidates, closed quests, expired deadlines and reviews that are 30 days old. An already-open browser page uses the same deadline and review-date rules to hide expired quest actions.
- Use `status: draft` for unpublished articles. Review sources and text before setting `approved`. Give each actual translation its own entry under `copy`. Check original records before publishing an application account and omit personal information. The initial article uses Yamanashi’s published rules as a worked example.

## Application effort

Record `application` only after checking official organizer rules. Its source URL must be the approved primary or supporting source. Record the review timestamp, whether entry is web-only, whether an SNS account or free organizer membership is required, supported platforms, and the actions on the shortest verified path. Use null for unresolved flags. The publication pipeline calculates the action count and difficulty from these facts. It prioritizes free, SNS-free web entry, then confirmed SNS-free routes and low-effort social routes. Writing a new or quote post and linking accounts count as more involved. Feed discoveries begin with unknown values and remain in the review queue until the organizer evidence is checked.

## Reader RSS

The site build emits `/ja/feed.xml` and `/en/feed.xml` from the current public opportunities and quests. Each feed keeps up to 20 items first published in the past 30 days. Listings with no recorded first publication, ads, affiliate listings, unpublished or expired listings, guides and archives are excluded.

In `data/rss-publications.json`, record a listing's existing route key (`quests/<id>` or `opportunities/<id>`), the actual languages first published together, the UTC completion timestamp of the first successful production deployment that exposed those details, and its evidence URL. Confirm that the pages were reachable in that release. If another language goes live later, add its own dated entry. A date is optional for the listing to work and required for RSS. If the first release cannot be substantiated, leave it out of this registry.

Keep the route key and first publication timestamp when editing content, updating the review or extending a deadline. The stable GUID uses the route key and language. A new timestamp is reserved for a genuinely new listing. Add the publication evidence after verifying the first release. The next normal site build will update the feed.
